# ui-review　UI 优化方案技能

> 原名 `ui-optimization-proposal`，为便于记忆已简化为 `ui-review`。GitHub 仓库同步更名为 `Yddply/ui-review`，旧地址会自动跳转，历史克隆不受影响。

把「实现和设计稿对不上」变成一份**可评审、可执行**的 UI 优化方案：每个数字都有实测来源，每处偏差都有代码级根因，每一行都写明归属前端还是后端 —— 最后产出可离线打开的单文件 HTML，并可同步到飞书云文档。

不是截图堆砌，也不是一份「感觉不太对」的清单。产出里所有数值均由机器读取：实现侧取浏览器的 `getBoundingClientRect()` / `getComputedStyle()`；设计稿侧则按其形态取 —— 高保真 HTML 可精确读取，**截图则按比例推算并全部标注 `估算`**，绝不冒充实测值。

## 一、用途：这个技能解决什么问题

**输入**：一份**设计稿**（基准，"应该长什么样"）+ 一个现状（"实际长什么样"）。设计稿**默认用高清截图** —— 不需要任何账号或令牌；有高保真静态 HTML 则精度更高，但那是**按需升级**，不是入场条件。
**输出**：两者之间的差异清单，逐项带实测数值、代码级改法、归属人，以及一份能直接发给评审的文档。

### 基准的三级阶梯：截图优先

为一次比对专门去申请账号或 API 令牌并不划算。所以基准默认是**人人都有**的截图，高精度基准是**按需升级**，不是一上来就索要。

| 层级 | 基准 | 精度 | 什么时候用 |
|---|---|---|---|
| **1 默认** | 高清截图（2x 导出） | 精确指标只能估算 | 永远从这里开始。不需要账号、令牌或他人配合。 |
| **2 升级** | 设计同学导出的高保真静态 HTML | 精确 | 仅当触发升级条件（见下）。仍然不需要令牌。 |
| **3 已有才用** | 设计源文件链接（如 Figma） | 精确 | 仅当你本机已有可用凭据，或你主动提供。**技能不会向你要任何令牌。** |

**升级条件（两条同时满足才提）**：① 已经历三轮以上「改 → 复测」，你仍不满意；② 剩余分歧落在截图看不出来的量上（精确字号、描边宽度与对齐、内边距、相近色差）。满足时我会请你找**设计这份稿的同学**导出一份高保真静态 HTML（导出一次即可，不是重做一版），基线随即钉死，之后每处偏差都能双向归因。

适用场景：

| 场景 | 说明 |
|---|---|
| 设计稿 vs 线上 | UI 还原度比对、样式偏差排查 |
| 改前改后对照 | 出一个改动前后的视觉对比方案 |
| 组件级排查 | 弹窗、卡片、表单、时间轴等单个组件的尺寸/字号/间距/配色偏差 |
| 跨端一致性 | 同一组件在移动端 H5 / PC 门户 / 小程序之间的不一致 |
| 差异归档 | 把上面这些整理成文档，并同步到飞书云文档供团队评审 |

**不适用**：

- 从零做设计 —— 本技能假设基准已经存在，不负责创造基准。
- 纯功能需求开发 —— 不涉及"比对"的任务不需要它。
- 主观审美评价 —— 本技能只处理可测量的偏差，不处理"我觉得不好看"。

## 二、产出什么

单次运行会产出以下六项：

1. **精度对照表** —— 逐项列出「设计稿实测值 vs 实现实测值」，每行带一个判定（`一致` / `偏差` / `不可比`）和一个归属人。
2. **改前/改后对比** —— 由**真实 DOM** 构建，不是截图。左右两栏用编号标注，按编号配对。
3. **逐项改法** —— 精确到「改哪个选择器、与哪条声明冲突」，并提示照抄会踩的坑。
4. **人力/资源分工表** —— 交付物、归属（前端 / 后端 / 设计 / 数据）、依赖、影响面、风险、灰度。
5. **离线单文件 HTML** —— 可直接用 `file://` 打开，无需登录、无需联网。
6. **飞书/Lark 云文档** —— 含两个可渲染的 `html5-block` 预览区块和可复制的代码块。

## 三、安装

技能本体就是仓库根目录（根目录里有 `SKILL.md`），所以**克隆下来的目录名就是技能名**。

### 方式一：装到用户级（推荐，所有项目可用）

```bash
git clone https://github.com/Yddply/ui-review.git ~/.workbuddy/skills/ui-review
```

Windows（PowerShell）：

```powershell
git clone https://github.com/Yddply/ui-review.git "$env:USERPROFILE\.workbuddy\skills\ui-review"
```

### 方式二：装到项目级（团队共享，随项目走）

在项目根目录执行：

```bash
git clone https://github.com/Yddply/ui-review.git .workbuddy/skills/ui-review
```

### 方式三：手动复制

把整个仓库目录复制到 `~/.workbuddy/skills/`（用户级）或 `<项目>/.workbuddy/skills/`（项目级）下，目录名保持 `ui-review`。

### 安装后验证

1. **重启会话**（或重新加载技能），让技能被扫描到。
2. 说一句应该命中它的请求，例如「设计稿截图我发你，线上是 `<链接>`，帮我查样式偏差」（换成高保真 HTML 也可以）。技能会在加载瞬间打印一段中文使用说明，看到说明即安装成功。

> 两个层级的关系：用户级是个人全局可用；项目级只在该项目内可用。同名的项目级技能会覆盖用户级。

## 五、什么时候需要先补充信息

「先追问一轮」**不是默认动作**，它是一次打断。只有在「问出来会改变产出」时才值得触发。

判定方式：对五个维度打分，每项 20 分。

| 维度 | 20 分 = 明确 | 10 分 = 含糊 | 0 分 = 缺失 |
|---|---|---|---|
| 优化对象 | 说清是哪个页面 / 组件 / 流程 | "整个 App" 或只给了大概区域 | 没提 |
| 基准来源 | 能用的设计稿 —— 高清截图就够；高保真 HTML 或设计源文件链接更好 | "在设计稿里，具体哪个不确定"，或只有一张被压缩过的 1x 截图 | 没有 |
| 现状来源 | 线上链接 / 源码或构建产物目录 | 只有截图 | 没有 |
| 交付去向 | 本地 HTML / 飞书 / 两者都要 | "你看着办" | 没提 |
| 约束 | 至少说明一处禁区，或允许的改动尺度 | 只能意会 | 没提 |

**≥ 90 分（内容上等价于「四项明确 + 一项含糊」）→ 无需追问。** 直接复述一句确认，把那一处含糊记进文档的「待确认」章节，然后开工。

**< 90 分（即两项及以上含糊/缺失）→ 先追问一轮。** 只问缺口，绝不复问已答过的内容；最多四轮，第四轮结束无论问没问齐都必须开始动手。

### 明确无需追问的情况

- 用户一次给齐了基准、现状、范围和去向 —— 复述一句即可开工。
- 要求是「继续改上一份文档」—— 读现有文档即可，不重新采集基线。
- 用户明确说「先别问，按你的判断做」—— 按默认值推进，把假设集中写进「待确认」。

## 十、脚本用法

四个脚本都是独立的 Node 脚本。`verify-render.cjs` 依赖 `playwright-core`，它驱动本机已安装的 Chrome，不会下载浏览器。

```bash
# 把设计源文件节点子树拍平成报告（可选路径；省略凭据时会尝试从本地审计日志里恢复，不会向你索要）
node scripts/figma-node-dump.cjs <FILE_KEY> <NODE_ID> --out report.txt

# 从线上页面或构建目录里恢复 CSS，并把框架单位换算成 px
node scripts/extract-inline-css.cjs --url=https://<host>/<page> --out css.txt
node scripts/extract-inline-css.cjs --dir=./dist --filter=<component> --out css.txt

# 提取改前/改后两栏，产出独立的 HTML 区块
node scripts/build-side-by-side.cjs --src=proposal.html --outdir=./draft_x_folder \
  --before-selector=".ba-col.before" --after-selector=".ba-col.after"

# 实测渲染页面：5 项零值检查 + 样式断言
node scripts/verify-render.cjs proposal.html --width=1440 \
  --expect=".avatar:width=32px;.dot:boxShadow=/inset/"
```

## 十一、六条硬规则

这六条决定了方案「能不能用」。它们不是风格偏好 —— 破任何一条都产出过错误的文档。

1. **只实测，不目测 —— 但没测到的必须标明。** 实现侧一律机器实测（`getBoundingClientRect()` / `getComputedStyle()`）；基准侧能机器读就读（高保真 HTML 取 DOM，设计源文件链接取 `absoluteBoundingBox` / `style.*`）。**截图是默认基准，但它读不出精确值** —— 由截图推算的数值一律标 `估算` 并列入「待确认」，绝不冒充实测值。
2. **设计稿是唯一基准。** 线上实现是被审查对象。不要"折中"两者，也不要因为线上现在就是这样就认为它对。
3. **构建真实 DOM，不用截图。** 对比区块是活的 HTML/CSS —— 同一份结构、两层样式。截图无法 diff、无法按编号标注、放大后不可信。
4. **默认最安全最省事。** 优先纯表现层改动；已有 token 够用就不新增 token；任何会外溢到相邻面（PC 门户、打印/PDF、消息卡片、后台管理）的方案一律拒绝，除非用户明确要求。
5. **每一行都要有归属。** 每条结论标记 `前端` / `后端` / `后端可选` / `设计` / `数据`。没有归属的结论是半成品。
6. **收尾清理。** 工作脚本、数据 dump、中间报告在结束时全部删除，用户的项目目录里除交付物外不留痕迹。

## 十二、依赖要求

| 依赖 | 用途 | 必需性 |
|---|---|---|
| **Node.js 18+** | 运行内置脚本（用到全局 `fetch`） | 必需（用脚本时） |
| **设计源文件读取凭据**（如 Figma PAT，`File content: Read-only`） | 读取设计源文件 | **非必需**。截图与高保真 HTML 都不需要；仅当你本机已有凭据、或你主动提供时才用到 |
| **Chrome / Edge** | `verify-render.cjs` 驱动实测 | 用该脚本时必需 |
| **`playwright-core`** | 同上，需 Node 可解析到 | 用该脚本时必需 |
| **飞书/Lark 连接器**（`docx:document:create`） | Phase 5 发布云文档 | 仅发布阶段需要 |

> Phase 1–4 与离线交付物**不需要任何连接器**，仅发布到飞书时才需要。
> 基准是高保真 HTML 或截图时**不需要任何凭据**。只有基准为设计源文件链接时才可能用到：技能会先在 `~/.workbuddy/audit-log/` 里找一次历史凭据，找不到就退回截图基准，不会主动向你索要。

## 十三、注意事项

- **语言分工**：技能正文（SKILL.md 与 references）全英文；追问材料时的问句与选项、交付文档正文、飞书文档内容为简体中文。
- **飞书 HTML 块限制**：单个 `html5-block` 上限 500KB，文档可用宽度约 820px。构建脚本会报告体积并在超限时告警。
- **不要把整份交付物塞进一个 HTML 块**：只提取前后对比两栏，正文用原生文档块，保持可搜索可编辑。
- **工具行为异常时**，先读 `references/pitfalls.md` 再动手 —— 它记录的是真实导致过错误输出的那些坑。
- **基准默认走截图，不索要令牌**：默认以高清截图建立基准，数值按比例推算并标 `估算`；只有「改满三轮仍不满意 + 分歧落在截图看不出来的量」时才升级，请你找设计同学导一张高保真静态 HTML —— **全程不需要任何账号或令牌**。
- **技能示例需脱敏**：本技能是公开仓库，示例取自真实项目。新增示例时必须扫描并替换品牌名、内部域名、设计源文件 key、真实选择器、人名工号、令牌与链接，详见 SKILL.md 的脱敏对照表。
